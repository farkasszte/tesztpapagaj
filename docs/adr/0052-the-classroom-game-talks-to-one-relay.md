# The classroom game talks to one relay, not to every device

The Quiz Game's player-device mode needs a network, and the project it was adapted from (Class Gauntlet) answers that with a peer-to-peer mesh: the teacher's tab is the host, the PeerJS server only introduces the two devices, and TURN relays the ones a school firewall would otherwise block. That model is elegant where it works and unfixable where it does not.

**The mesh's cost is per-device, and it multiplies.** In a mesh every byte the teacher's tab sends is sent once per device: `#broadcast()` walks the connection list and sends each peer its own `view`, and `#sendPictures()` pushes the picture's bytes to each peer separately. A 512 KB picture in a 50-student class therefore leaves the teacher's laptop fifty times — 25.6 MB up a school uplink — while the same picture sent once through a relay is 512 KB. Measured against a Durable Object relay with 50 WebSocket clients: **5000 of 5000 views delivered in 213 ms, and one 512 KB upload reached all 50 students in 60 ms**, with the teacher's outgoing traffic staying at 512 KB. The mesh also opens 50 DTLS/SCTP handshakes at the start of the game and uses reliable, ordered channels, so one weak device stalls the room.

**So the rules stay, the transport changes.** The teacher's browser still owns the game — it runs the engine, decides what each screen may see, and saves after every change — and the relay deliberately knows nothing: no questions, no scores, no phases. It holds a room under a six-digit code, forwards a view to everyone or to one device, and keeps the pictures it was given once so a student who joins late (or comes back after a dropped Wi-Fi) gets them without another upload. Nothing about the game is duplicated on the server, which is why the relay is about three hundred lines and a new game mode never touches it.

**One WebSocket per device, and reconnection is the client's job.** The relay is a Cloudflare Durable Object per room code, accepted through the hibernatable WebSocket API, so a room costs nothing while the teacher is talking and its connections survive the object going idle. The browser client reconnects with exponential backoff up to eight seconds, sends a heartbeat every twenty seconds, and hands the caller a `welcome` on every return: the teacher answers it with a full view (the game already has one for every phase), and the student carries on from the seat in its own storage. A room holds 50 students; a 51st is told the room is full instead of quietly being dropped.

**Pictures are binary frames, not base64.** A picture travels as `TPP1` magic, a four-byte header length, a JSON header (hash, mime) and the bytes, in both directions; base64 would add a third to every image on a network that is already the weak part. The relay keeps them in memory, never in the Durable Object's storage, whose 128 KiB value limit is smaller than a schoolbook scan; if a room goes cold and loses them, the relay asks the teacher's tab for the picture again (`picture-missing`) rather than showing a hole in the question.

**The cost of this decision is one deployed thing.** Cloudflare Workers and Durable Objects on the free plan, no database, no PeerJS server, no TURN credentials, and the app itself stays static and where it is. The relay lives in `workers/room/` and is deployed with `bun run deploy:room`; the browser needs `VITE_ROOM_URL` pointing at it. The alternative — writing our own mesh — would repeat the same arithmetic with more code, and the mesh's own arithmetic is what fails at fifty.
